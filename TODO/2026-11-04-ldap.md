# LDAP: a writable front end on the directory

The maintainer, 2026-11-04: Lugh's LDAP is "level 2" of the three set out that day: writable, mapped
onto Lugh's own model, with the LDAP listener as a second front end on `Directory` exactly
as `/api/v1` is the first. It is not a general-purpose LDAP server: no operator-defined
schema, no arbitrary tree, no LDAP ACLs, no replication over LDAP. Those would invert the
directory model, and are OpenLDAP's job. This document is the design and the plan; it
replaces the P9 row in `ACTIVE.md` and answers open question 5 in `docs/architecture.md`.
Nothing here is built yet.

Each statement is **Settled** (the maintainer's decision, with where it is written) or **Proposed** (a
recommendation for the maintainer). What waits on him is collected at the end.

## What it is for

Software that speaks LDAP and nothing else: mail servers, NAS boxes, VPN concentrators,
Linux PAM and SSSD, and the admin pages those have for changing a password or putting a
user in a group. They need to bind as a user to check a password, search people and groups,
and sometimes write back. They do not need a schema of their own.

## The tree (Settled in architecture.md, "LDAP surface"; the details Proposed)

The tree is fixed and generated from the directory. Nothing is stored as an LDAP entry;
every entry is a view of a `User`, a `Group` or the tree itself.

```
<base>                                     dc=..., from ldap.base_dn
  ou=people,<base>                         persons
    uid=<name>,ou=people,<base>
  ou=services,<base>                       service users (Kind::service)
    uid=<name>,ou=services,<base>
  ou=groups,<base>
    cn=<name>,ou=groups,<base>
```

Services live apart from people so a PAM or mail client that searches `ou=people` never
sees an account that cannot sign in interactively. A bind is allowed from either.

### Entries

| Entry | Object classes | Attributes, from |
|---|---|---|
| Person | `top`, `person`, `organizationalPerson`, `inetOrgPerson`, `posixAccount` | `uid` = name; `cn` and `displayName` = display name; `givenName`, `sn` (below); `mail` = email; `uidNumber`, `gidNumber`, `homeDirectory`, `loginShell` (below); `memberOf` = the DNs of its groups; `entryUUID` = the user ID; `createTimestamp`, `modifyTimestamp` |
| Service | `top`, `person`, `organizationalPerson`, `inetOrgPerson` | As a person, less `posixAccount` and `mail` when empty |
| Group | `top`, `groupOfNames`, `posixGroup` | `cn` = name; `description`; `member` = the DNs of its members; `gidNumber`; `entryUUID`, timestamps |
| `ou=...` | `top`, `organizationalUnit` | `ou` |
| `<base>` | `top`, `dcObject`, `organization` | `dc`, `o` |
| rootDSE | | `namingContexts`, `supportedLDAPVersion` (3), `supportedControl`, `supportedExtension`, `supportedSASLMechanisms` (none), `vendorName`, `vendorVersion` |

`uid`, `cn` and `mail` are matched case-insensitively, as `Directory` folds them.

**`givenName` and `sn` (Proposed, the maintainer's call).** `inetOrgPerson` requires `sn`, and OIDC's
`profile` scope wants `given_name` and `family_name` (P6). Lugh holds only `display_name`.
Add `given_name` and `family_name` to `User`, optional, exposed by the API as
`given_name`/`family_name` and by LDAP as `givenName`/`sn`, and the ID token's claims come
from the same fields. The alternative, deriving `sn` from the last word of the display
name, is wrong for most of the world's names and is not recommended. Until the fields are
set, `sn` is the display name whole, so the entry is still valid.

**POSIX numbers (Proposed).** `uidNumber` and `gidNumber` are allocated once, at creation,
from `ldap.posix.uid_range` and `ldap.posix.gid_range`, and never reused: a removed user's
number dies with the tombstone. The allocation is a counter record per range in a
`counters` table, advanced by compare-and-set against its version, so two creations on one
node cannot share a number. On Dagda (P8) that counter is a single-use thing, and follows
the single-use rule in architecture.md, "Consistency": each node leases a block of numbers
from the counter and allocates within it, so a partition cannot hand the same number out
twice. A user made before the LDAP range was configured has no number and no
`posixAccount` class until an administrator sets the range, after which numbers are
allocated on first read in a deterministic order (by creation time, then ID), on one node,
and written. `homeDirectory` is `ldap.posix.home` with `{name}` substituted
(`/home/{name}`), `loginShell` is `ldap.posix.shell` (`/bin/bash`); neither is stored.
Each user's primary `gidNumber` is a configured group's (`ldap.posix.primary_group`, by
name) or, absent that, their own `uidNumber`, which is the user-private-group convention
Linux distributions use.

## Operations (Settled: the list in architecture.md; the writes Settled, the maintainer 2026-11-04)

| Operation | Does |
|---|---|
| `BindRequest` | Simple bind only, with a DN from the tree, over TLS only; `simple` with an empty password is refused (`inappropriateAuthentication`), never treated as anonymous. SASL: `authMethodNotSupported`. What a bind proves is below |
| `SearchRequest` | Scopes `base`, `one` and `sub`; the filter grammar below; size, time and paged-results limits |
| `CompareRequest` | One attribute of one entry, under the same read rights as a search |
| `AddRequest` | A person, a service or a group, under its `ou`. Exactly the object classes above, and only the attributes Lugh stores; anything else is `objectClassViolation` or `noSuchAttribute` |
| `ModifyRequest` | `replace` and `delete` of the writable attributes; `add` of `member`, `delete` of `member`, `replace` of `member` on a group. The whole modify is one directory change: it succeeds or fails entire |
| `DeleteRequest` | A user (final, with their memberships, password and factors, as the API's `DELETE`) or a group |
| `ModifyDNRequest` | A rename: `uid=` or `cn=` to a new value under the same parent. `newSuperior` is `unwillingToPerform` |
| `AbandonRequest` | Stops a search still streaming results |
| `UnbindRequest` | Closes |
| `ExtendedRequest` StartTLS (1.3.6.1.4.1.1466.20037) | On the plaintext listener; refused once TLS is up |
| `ExtendedRequest` Who am I? (RFC 4532) | The bound DN |
| `ExtendedRequest` Password Modify (RFC 3062) | Below |

Controls: paged results (RFC 2696) on search; the Assertion control (RFC 4528) on every
write, which is how an LDAP client gets the API's `If-Match`. A critical control not listed
is `unavailableCriticalExtension`; a non-critical one is ignored. Everything not in the
table is `unwillingToPerform` with a message naming this document's rule.

### Writable attributes

| Attribute | Write | Lugh field | Rule |
|---|---|---|---|
| `uid` (via ModifyDN) | rename | `name` | `normal_name()`, unique |
| `cn`, `displayName` | replace | `display_name` | both set the one field; `cn` cannot be deleted |
| `givenName`, `sn` | replace, delete | `given_name`, `family_name` | if the maintainer accepts the fields |
| `mail` | replace, delete | `email` | `normal_email()`, unique; a person must keep one |
| `description` | replace, delete | group `description` | |
| `member` | add, delete, replace | memberships | each value a DN in the tree, else `noSuchObject` |
| `userPassword` | never | | `unwillingToPerform`: Password Modify is the only way |

Read-only attributes (`memberOf`, `uidNumber`, `entryUUID`, the timestamps, the object
classes) answer `constraintViolation` to a write. `objectClass` cannot be changed.

### Filters

Equality, presence, substring (initial, any, final), `and`, `or`, `not`, with bounded
nesting depth (16) and size. `approxMatch` is treated as equality. `greaterOrEqual` and
`lessOrEqual` match on `uidNumber` and `gidNumber` only. Any other combination of
attribute and match evaluates to Undefined, as RFC 4511 section 4.5.1.7 provides, so an
unsupported filter never errors, it just matches nothing. A filter on an attribute the
entry does not have is Undefined for that entry.

Evaluation is in memory over the users or groups the search scope covers, read once per
search through `Directory::users()`, `groups()` and the memberships, with no index. That
is right for a directory of thousands, which is what Lugh is for, and wrong for millions,
which it is not; the size limit bounds the answer and the time limit the work.

## What a bind proves, and what it may then do

Settled (architecture.md, "LDAP and the second factor"; the scopes Proposed):

- A person whose policy is `pwd` may bind with their main password. Lugh runs
  `Authenticator::password()`: the back-off, lockout and audit are the sign-in's, and a
  `next` that stops at the second factor is refused (`invalidCredentials`) because LDAP
  cannot carry one.
- A person whose policy needs more, and every service, binds with an **app password**
  (P11's design; this plan pulls them forward, below): random, shown once, Argon2id,
  named for the device, limited to LDAP and optionally to source networks, revocable alone.
- A bind as a disabled, unknown, unenrolled or non-existent user, and a wrong password, all
  answer `invalidCredentials` after the same work.

After the bind, the connection has a `Caller`, the same type `/api/v1` resolves, and every
operation is checked against the API's scopes before `Directory` is asked (so the IoC check
and the scope rule hold here too):

| Bound with | Caller's scopes |
|---|---|
| Main password | Those the user's groups grant (P6's rule: a session's scopes come from its groups) |
| App password | The user's identity, and `lugh:directory.read` at most: an app password never writes |

Then:

- An entry may always read and compare itself.
- Search and compare elsewhere need `lugh:directory.read`; an entry the caller may not
  read is not there (`noSuchObject`, or absent from results), never
  `insufficientAccessRights`, so the tree does not leak.
- Add, modify, delete and rename need `lugh:directory.write`.
- **Password Modify** changes the bound user's own password only, and only when the bind
  was the main password: a `pwd` user changing their own. The old password is required in
  the request. An app password can never change the main one, and an administrator cannot
  set someone else's password over LDAP (nor over the API: the enrolment link is the one
  way), so `userIdentity` naming another entry is `unwillingToPerform`. A change goes
  through `Passwords::set()` with its rules and breached list, and revokes the user's
  sessions when P6 has them.

A connection that binds again is a new caller; one that unbinds, or whose bind fails, is
anonymous and may do nothing but bind, StartTLS and read the rootDSE.

## Results, concurrency and audit

- Every operation is one `Directory` (or `Authenticator`, `Passwords`) call in Dannan's
  shape, with the route deadline; the connection waits on nothing.
- `Outcome` faults map to result codes: `refused` to `constraintViolation`,
  `entryAlreadyExists` (a name or address taken), `noSuchObject` or
  `notAllowedOnNonLeaf` by what was refused; `failed` to `unavailable` with "the request
  could not be completed", as the API's 500. A write past its deadline says, in
  `diagnosticMessage`, that it may yet be made.
- An Assertion control carrying `(entryVersion=<n>)` makes the write conditional on the
  entry's version, as `If-Match` does, and a stale one is `assertionFailed` (the API's
  412). `entryVersion` is an operational attribute readable by anyone who may read the
  entry. Without the control, the write is made against the version just read, as
  `Directory` already does for every caller.
- Every bind, write and Password Modify is audited with the actor (the bound user's ID)
  and the source (`ldap:<address>`), in the same entries the API makes; a search is not.

## Transport and limits

- LDAPS on `ldap.port` (636) and StartTLS on `ldap.starttls_port` (389), both optional;
  with neither set there is no LDAP listener. Plaintext never carries anything but
  StartTLS and the rootDSE; a bind before TLS is `confidentialityRequired`.
- TLS comes from the same `TlsContext` as HTTPS: TLS 1.3 only (Proposed: no TLS 1.2 for
  old clients; a client that cannot do 1.3 goes through stunnel or is replaced; the maintainer's call,
  open question 5's second half).
- The listener is Lugh's, as HTTP is (the maintainer, 2026-11-04: HTTP stays Lugh's), in `lugh/ldap/`
  on Asio: an acceptor, a TLS handshake with the HTTP server's handshake deadline, then
  one connection object reading BER messages. Per connection: at most `ldap.most_pending`
  (8) operations in flight, an idle timeout, a message size cap (64 KiB; a search over a
  thousand entries is written, never read), and a bounded result stream that stops at the
  size limit. The rate limiter and `ClientAddress` are the HTTP ones.
- Shutdown: stop accepting, let binds in flight answer, close.

## The code

```
lugh/ldap/
  ber.h/.cpp            bounded BER decoder and encoder: tag, length, depth and total caps
  messages.h/.cpp       LDAPMessage, the operations, controls and result codes (RFC 4511)
  filter.h/.cpp         the filter tree, parsed from BER, evaluated against an Entry
  dn.h/.cpp             DN parsing and normalisation (RFC 4514), only the forms the tree has
  tree.h/.cpp           Entry, and the generated tree over Directory: read, locate, enumerate
  authz.h/.cpp          Caller from a bind; what each operation needs
  operations.h/.cpp     each operation over the tree, in Dannan's shape, answering results
  password_modify.cpp   RFC 3062 over Passwords and Authenticator
  connection.h/.cpp     one connection: framing, pending ops, abandon, StartTLS
  ldap_server.h/.cpp    the acceptor
lugh/authn/
  app_passwords.h/.cpp  P11's app passwords, brought forward
lugh/test/
  ldap_*_test.cpp       units per file above
  fixtures/ldap_client.h  a small LDAP client over Asio and the same BER, for the process test
  node_process_ldap_test.cpp  the real lugh-node over LDAPS and StartTLS
lugh/fuzz/
  ber_fuzz.cpp, filter_fuzz.cpp, dn_fuzz.cpp
```

`Directory` grows nothing LDAP knows about except the fields above (`given_name`,
`family_name`, the POSIX number) and `counters`; the mapping to DNs is `tree.cpp`'s, so a
rename of the LDAP layout touches one file. The API gets the same fields in the same step.

## Tests

From RFC 4511, 4512, 4514, 4517, 4519, 2696, 4528, 3062, 4532 and this document, never from
the behaviour:

- BER: every length form, indefinite length refused, depth and size caps, truncation at
  every byte of a valid message (a test that walks them), and the fuzz target.
- DN: the forms in the tree, escaping, case folding, and everything else refused.
- Filters: each kind, nesting to the cap and one past it, Undefined where the document
  says, evaluated against entries with and without the attribute.
- The tree: each entry's attributes from a `User` or `Group`, `memberOf` and `member` agreeing,
  POSIX allocation never repeating a number across removal and re-creation, services apart
  from people.
- Each operation: the rights table above, every result code the document names, the
  Assertion control fresh and stale, Password Modify by the owner, by an app password
  (refused) and naming another (refused), rename collisions, deleting a user removing their
  memberships and factors, a modify that fails entire.
- Bind: `pwd` user with main password; `mfa` user with main password refused and with app
  password accepted; back-off through LDAP counting with the API's; empty password refused;
  plaintext bind refused.
- The connection: pending-operation cap, abandon, idle timeout, StartTLS then refused
  twice, a message over the cap closing the connection.
- Process: `lugh-node` with `ldap.port` set, a bind, a search, a modify and a Password
  Modify over LDAPS from the fixture client; the same over StartTLS; no listener when
  unconfigured.

Every phase ends green under ASan with UBSan and under TSan, as `CLAUDE.md` says, with the
test counts in `COMPLETED.md`.

## The steps

Replaces P9 and moves app passwords out of P11. Each is a commit with its tests.

| Step | What |
|---|---|
| **L1** | The fields: `given_name`, `family_name` and the POSIX number on `User`, `counters`, the API's `given_name`/`family_name`, `docs/api.md`. Small, and P6's `profile` claims want it too |
| **L2** | App passwords (P11's design, unchanged): the table, create/list/revoke in `Directory`'s dependents, the API routes under `/api/v1/users/{id}/app-passwords`, verification with the same back-off |
| **L3** | BER, messages, DN and the filter tree, with their fuzz targets. No network yet |
| **L4** | The tree over `Directory`, rootDSE, and read-only operations: bind, search (with paging and limits), compare, Who am I?, unbind, abandon. The connection, LDAPS and StartTLS, the server, the config keys, the process test |
| **L5** | Writes: add, modify, delete, rename, the Assertion control, Password Modify. The audit entries. `docs/ldap.md` written from this document, and the architecture's LDAP surface pointing at it |

L1 and L2 can go before or after P6 and do not depend on it; L4 is the first LDAP that
serves, and is useful on its own. L3 to L5 depend on nothing in P6 or P8, so the order
with those phases is the maintainer's. On P8 the only change is the POSIX counter's lease.

## Not built, and why

- Operator schema, `subschemaSubentry` beyond the fixed one, custom object classes or
  attributes: entries would have to be stored as entries, inverting the directory.
- Arbitrary DNs, `newSuperior`, aliases, referrals, subordinate naming contexts.
- LDAP ACLs: rights are Lugh's scopes, and set in one place.
- SASL (PLAIN would carry a password no better than simple bind; EXTERNAL would need
  client certificates Lugh does not issue to users; nothing in SASL carries a second
  factor).
- Server-side sort, VLV, persistent search, syncrepl: nodes replicate through Dagda, and
  a client that needs change notification uses the audit log or webhooks (P12).
- Anonymous reads.
- `userPassword` as an attribute, in either direction.
- Writing `memberOf` (it is `member`'s reflection), `uidNumber`, `gidNumber`, `objectClass`.

## For the maintainer

   name (not recommended).
2. TLS 1.3 only on LDAP (recommended), or TLS 1.2 as well for old clients.
3. App passwords brought forward from P11 into L2 (recommended: without them an `mfa` user,

4. Services under `ou=services` (recommended), or in `ou=people` with everyone else.
