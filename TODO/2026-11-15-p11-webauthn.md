# P11: WebAuthn, passkeys and the `phr` level (plan, 2026-11-15)

The maintainer, 2026-11-15: P11 before the dashboard (P7), so the dashboard requires `phr` from the start. The design already stated in
`docs/architecture.md` ("Two-factor authentication") holds; this plan says how it is built and what is still open.

## What the design already says

- WebAuthn credentials (security keys and platform authenticators, passkeys) are a factor. Lugh stores each credential's ID,
  public key, sign count, AAGUID and transports.
- With user verification (UV), a passkey alone is `phr`: two factors in one, and no password.
- A password plus a WebAuthn assertion without UV is also `phr`. The authenticator is phishing-resistant, and the password is
  the second factor.
- `amr` records what was used (RFC 8176): `hwk` or `swk`, plus `user` or `pin` when UV was done, plus `pwd` when a password
  was used.
- A sign count that goes backwards is refused and flagged. Authenticators that always report 0 (synced passkeys) are exempt
  while both counts stay 0.
- Lugh's dashboard and anything that administers infrastructure require `phr`.
- Root's first sign-in enrols a WebAuthn credential, since the dashboard needs `phr`.
- An administrator must be at `phr` to reset another user's factors.

## Steps

| Step | What |
|---|---|
| **W1** | CBOR (RFC 8949): a strict, bounded decoder for what WebAuthn sends (maps, arrays, byte and text strings, integers, simple values; no indefinite lengths, no tags). Then COSE keys (RFC 9052): EC2 P-256 (-7, ES256), OKP Ed25519 (-8, EdDSA) and RSA (-257, RS256). Each has a fuzz target. Where it lives is open (question 2) |
| **W2** | The ceremonies, with no network: registration (`clientDataJSON` type, challenge, origin; `rpIdHash`; the UP and UV flags; attested credential data; the attestation statement per question 1) and assertion (the same checks, the signature over `authData` and the hash of `clientDataJSON`, the sign count). Tested from the W3C WebAuthn Level 3 test vectors and from recorded ceremonies of real authenticators |
| **W3** | `Factors` gains `webauthn`: register begin and finish, assert begin and finish. Challenges are single-use, held for 5 minutes in the node's grants, as codes are. Credentials go in the factor table. Several credentials per user, each named; removal under the existing last-factor rule |
| **W4** | The sign-in pages: one small first-party script (`/signin/webauthn.js`, `script-src 'self'`, no inline script) calling `navigator.credentials`. A "Sign in with a passkey" button for discoverable credentials (no name typed), and a security key as the second step after a password. Enrolment and adding a key from `/signin/factors`. Pages without the script still work for password plus TOTP |
| **W5** | `phr` is real: the sign-in reaches it, sessions and tokens carry it, the policy routes accept it, and an application or `acr_values` that requires it is met instead of refused (`flow_routes.cpp`'s guard goes). The OAuth metadata lists it. Step-up from `mfa` to `phr` asks only for the WebAuthn assertion |
| **W6** | Root's first sign-in requires a WebAuthn credential (genesis then enrolment). An administrator's factor reset requires `phr`. The API exposes credentials (`GET` and `DELETE /api/v1/users/{id}/factors` gains `webauthn`, with name, AAGUID and last use) |
| **W7** | Process tests on the real `lugh-node` with a software authenticator in the test fixtures (a P-256 key making real attestation and assertion objects): enrol, sign in passwordless, step up, a cloned authenticator's counter refused, a wrong origin refused, `phr` reaching an application's ID token |

## Progress

- W1 done (3b3a34f): CBOR, COSE keys, the `fuzz_webauthn` target (unbuilt until the fuzz targets are built on node-a).
- W2 done (8ce0934): the ceremonies, ES256 and EdDSA. RS256 assertions are refused until Dannan's `verify_rs256` is pinned. A
  software authenticator in `lugh/test/fixtures/soft_authenticator.h`, written from the specification apart from
  `lugh/webauthn`.
- W3 done (58c233a): WebAuthn credentials in `Factors`. An id registered to anyone is refused. The sign count is written at the
  version read.
- W4a done (40a6809): the authenticator's steps: a credential as the second factor, a passkey alone, enrolment by a credential.
  `phr` is reached by any WebAuthn ceremony (`amr` hwk or swk, and user when verified).
- Challenges (`authn/challenges.h`) are stateless when issued:
  - random bytes and an expiry, MAC'd under the process's own key and bound to the visitor's sign-in cookie;
  - so a passwordless sign-in holds nothing for an anonymous visitor, as the pre-sessions already ensure;
  - a claim marks one used, and a failed ceremony releases it, so only successes stay in the bounded used set;
  - when full, a claim is refused (fails closed).
- W4b next: the pages and the script. The RP ID is `oauth.issuer`'s host and the origin is the issuer's; WebAuthn is offered only
  when the issuer is set.

## Ruled (the maintainer, 2026-11-15)

1. **Attestation `none`**: any authenticator is accepted. The AAGUID is kept as the authenticator's claim, unverified. No FIDO
   Metadata Service.
2. **Where**: RS256 verification in Dannan, beside its ES256 and Ed25519 (asked of Dannan). CBOR and COSE in Lugh, under
   `lugh/webauthn/`, moving down to Dannan if a second user appears.
3. **RS256**: accepted, verification only, keys of 2048 bits and up.
4. **Passwordless for everyone**: the sign-in page offers "Sign in with a passkey" (discoverable credentials) beside the name
   box. A passkey with UV signs in alone at `phr`.

## Tests

From WebAuthn Level 3 and RFC 8949 and 9052, not from behaviour:
- Every registration and assertion check refuses on its own: origin, `rpIdHash`, challenge, type, UP, UV when required,
  signature, counter, algorithm.
- CBOR's limits (depth, length, duplicate map keys, non-canonical integers) refused.
- The fuzz targets run in P12's campaign.
- The process tests in W7.
- Debug, ASan and TSan at the phase's end, as always.
