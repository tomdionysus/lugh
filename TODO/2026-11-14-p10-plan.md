# P10: `lugh_client`, the C++ library

Started 2026-11-14 (the maintainer: the work while Dagda's slice 1 is awaited). From `docs/architecture.md` ("Library"), the P6 design
(`2026-11-04-oauth.md`), and what Lir has built against it (`../lir/lir/auth/tokens.h`, read 2026-11-14).

## What Lir needs, first

Lir's seam is `lir::auth::TokenVerifier`:

```
virtual std::variant<TokenClaims, std::string> verify(std::string_view token, dannan::contract::TimePoint now) const = 0;
```

Synchronous, on the broker's strand, waiting on nothing: it answers from keys fetched and cached before. `TokenClaims` carries
the subject, the audiences, the scopes (split on spaces), `exp`, whether the token is bound to a DPoP key (`cnf.jkt`, which Lir
refuses) and the certificate thumbprint it is bound to (`cnf.x5t#S256`, 32 bytes, matched against the client's certificate). Lir
checks its own audience (`lir`) and its topic scopes (`lir:(pub|sub|retain):<filter>`); the signature, `kid`, `typ`, `iss`, `nbf`
and `exp` are Lugh's to check (RFC 9068). The token comes as the MQTT CONNECT password or the `lugh` auth method. Lir has no
implementation yet, only a table fake, and has not wired its authenticator into `lir-node` "until the linking question is answered".

## The shape proposed

- **`lugh::client::Verifier`**: `verify(token, now)`, synchronous, from the key set it holds: the compact JWS parsed with the
  rules `lugh/tokens/jose.h` has today (ES256 or EdDSA, a `kid`, no header but `alg`, `kid`, `typ`), `typ` `at+jwt`, the key by
  `kid`, `iss` one of the configured issuers, `exp` and `nbf` with Lugh's skew, a `cnf` that binds to something known. Answers
  the claims or the reason. An opaque token (Lugh's `lugh_o_` handles) cannot be verified offline and is refused with that
  reason.
- **`lugh::client::KeySource`**: where the keys come from, behind an interface. The first is HTTPS: discovery
  (`/.well-known/openid-configuration`), then `jwks_uri`, in Dannan's callback shape (executor, deadline, `done` posted), refreshed
  on a schedule and on an unknown `kid` (at most once a minute), keeping the last good set when a fetch fails. Later, retained
  values in `lugh/scope` (P8), behind the same interface.
- **Several issuers**: one site's Lugh is one issuer (architecture, question 14), so a verifier holds a key set per issuer and
  picks it by `iss` before the signature is checked.
- **One copy of the code**: `jose` and the access-token checks move into the library, and `lugh-node`'s `TokenIssuer::verify`
  calls the library's for the signature and claims, adding only what a node alone knows (opaque handles, revoked `jti`s).
- **Stated limits**: offline verification cannot see a revocation; an access token is honoured until its `exp` (Lugh's access
  tokens are short-lived by each application's setting). Introspection is the way to ask, and is online.
- **Packaging**, by the stack layout (`../CLAUDE-STYLE-2026.md`): public headers under `lugh/include/lugh/client/`, included as
  `"lugh/client/x.h"`; the library's own sources in `lugh/client/` (with `jose` moved there from `lugh/tokens/`); a `lugh_client`
  target exported as `lugh::client` in the `lugh` package (`find_package(lugh 0.x CONFIG)`, `SameMinorVersion`), which the node's
  `lugh` library links. Built without the node, its store or its HTTP server under a `LUGH_BUILD_NODE` option, so a consumer
  that fetches Lugh builds only the library. A move is its own commit, with no change of content.
- **One Dannan per process** (Lir, 2026-11-14): a consumer that pins a Lugh commit must get the Dannan it already links. Lugh,
  fetched into another build, uses the consumer's `dannan::dannan` when that target exists (FetchContent's first declaration of
  `dannan` wins, and Lugh fetches its own only when none is there), and the commit named to Lir says which Dannan it was built
  and tested on (0.7.0 now, as Lir is moving to).

## P10.0, what moves (mapped 2026-11-14)

- `lugh/tokens/jose.{h,cpp}` needs only Dannan (`identity/signing.h`, `identity/crypto.h`), Boost.JSON, and two pieces of
  Lugh's core: `lugh/core/secure_bytes.h` (Dannan's `Bytes` and `SecureBuffer` aliases, header-only) and `lugh/core/encoding.h`
  (hex, base64url; header-only). Those two go with it, so `lugh_client` depends on nothing of the node's. Its users today: the
  issuer, client authentication, DPoP, the signing keys, the JWS fuzz target, and six test files.
- The order, each a commit: move `jose` to `lugh/client/` with its includes followed (no other change); rename
  `lugh::tokens` to `lugh::client` in it (a rename); move `secure_bytes.h` and `encoding.h` under the client library's reach;
  then the `lugh_client` target, with `lugh` linking it; then `LUGH_BUILD_NODE`, the export and package config. One debug run
  on a build node at the end of each that changes the build.
- **Boost.JSON is the snag.** Its definitions are compiled once, in `lugh/http/boost_json.cpp` (`boost/json/src.hpp`). The client
  needs them too, and a consumer that also compiles them (Lir does not today) would collide. Proposed: they move into
  `lugh_client`, and the package says a consumer of `lugh::client` takes Boost.JSON from it; or the library links Debian's
  compiled `Boost::json` instead, which is cleaner for consumers but adds a compiled Boost library to the stack's list. A
  question for the maintainer when P10.0 reaches it, with the first recommended (no new dependency).

## Later in P10

The flows (authorisation code with PKCE, client credentials, device), introspection, and a management API client, as the
architecture lists them. None is on Lir's path.

## Ruled (the maintainer, 2026-11-14)

1. **`lugh_client` links Dannan**, for its signing and its time types; the architecture's "OpenSSL and Boost only" is changed to
   say so. No JOSE code is duplicated.
2. **Lugh is only one possible way for Lir to authenticate.** `lugh_client` knows nothing of Lir; the adapter that implements
   Lir's `TokenVerifier` over `lugh::client::Verifier` is Lir's optional Lugh plugin, and Lir builds without Lugh when it is off.
   The library's verifier is shaped so that adapter is a few lines: synchronous, from cached keys, Dannan's `TimePoint`, the
   claims Lir's `TokenClaims` holds.
3. **Lir pins a commit on `develop`** with `FetchContent` until Lugh cuts a release, building the library only.
4. **All of P10 together**: the verifier and key sources, the flows (code with PKCE, client credentials, device), introspection
   and the management API client are built as one phase before Lir integrates.
